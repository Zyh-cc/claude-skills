# 修 Bug 通用流程：先定位，再动手，修完验证

## 版本日志
| 版本 | 日期 | 变更内容 |

## 五条核心原则

### 1. 退化问题先找变化点，不要先猜根因

"之前好用，现在不行" → 第一步永远是找到**什么改变了**，而不是从原理推测。

有 git 记录时：`git log --oneline <文件>` → `git show <hash>`，答案通常就在变更里。
没有 git 时：回忆最近改了什么（配置、依赖、代码），在这里找，不在别处。

> 跳过这步直接推理，等于在没有线索时推理案件。

---

### 2. 根因要能说清楚，说不清楚就不动手

动手前必须能一句话说出：**"因为 X，所以出现了 Y"**。

"可能是 X 的问题" 不够——这是猜测，不是根因。  
"X 这个假设是错的" 才是——要用证据（文档/源码/help()/实验）来验证假设，不靠直觉。

写修复代码之前，先把这句话写出来。

---

### 3. 找到一处不等于找完了

定位到根因后，立刻问：**同一个问题还在哪里出现？**

- 同一次提交引入的其他改动
- 同一个模式在文件里出现的其他位置
- 同一个错误假设在其他地方的体现

全部列出来，一次修完，再提交。修一处就提交，常常导致"修了还是不行"。

---

### 4. 提交前自检：真的修完了吗？

提交前过一遍：
- 根因是否完全消除（不是绕过，是消除）？
- 是否存在同类问题没有一起修？
- 修复是否引入了新假设——这个新假设验证过吗？

如果三个问题都能回答"是/否/是"，再提交。

---

### 5. 修复失败时，先理解为什么失败，再想下一步

第一次修复没解决问题时，**不要立刻想下一个方案**。  
先问：我的修复为什么没有生效？哪个假设又是错的？

这和原则 2 一样：没有新的诊断就没有新的行动。
否则会陷入"一直在打补丁但问题没有消失"的循环。

## 反面教材（来自真实案例）

| 错误做法 | 导致什么 | 正确做法 |
|---------|---------|---------|
| 修完 `mouse_move` 回调就提交 | `mouse_button` 同样破坏拖拽，还是不行 | 修前先列出所有同类注册点 |
| 假设 `return False` = 不消费事件 | 修复方向错误，多花一倍时间 | 先用 `help()` 验证返回值语义 |
| 用 `x is None` 检查缓存是否初始化 | `0`（合法假值）绕过检查，缓存永远无效 | 用 `not x` 或明确区分"未初始化"和"假值" |
| 修复不生效时直接换方案 | 方案越堆越多，根因仍不清楚 | 先搞清楚为什么这次失败 |
