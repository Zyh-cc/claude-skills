# 修 Bug 通用流程

## 五条原则（按顺序执行）

**1. 退化问题先找变化点**
"之前好用，现在不行" → 先找**什么改变了**，不要先猜原理。
有 git：`git log --oneline <文件>` → `git show <hash>`。

**2. 根因要能说清楚才动手**
动手前能一句话说出："因为 X，所以出现了 Y"。
"可能是 X" 不够——用文档/`help()`/实验验证，不靠直觉。

**3. 找到一处，再找同类**
定位后立刻问：同一个问题还在哪里出现？（同一提交的其他改动、同一模式的其他位置）
全部列出，一次修完，再提交。

**4. 提交前自检**
- 根因完全消除（不是绕过）？
- 同类问题都修了？
- 新假设验证过？

**5. 修复失败时先理解为什么，再想下一步**
不要立刻换方案——先问：我的修复为什么没有生效？哪个假设又是错的？

---

## 常见陷阱

| 陷阱 | 正确做法 |
|------|---------|
| 修完第一个症状就提交 | 先列出所有同类问题再提交 |
| 假设 API 行为 | `help()` / 文档验证后再写修复 |
| 修复不生效直接换方案 | 先搞清楚为什么这次失败 |
| `x is None` 检查缓存 | 合法假值（0/False）会绕过，用 `not x` |
